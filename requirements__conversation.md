# Conversation Poll Requirements

## Background
- Repeated or near-duplicate bot replies are showing up in the live chat flow.
- Current conversation state is split across multiple places (thread history, in-memory histories, FAISS).
- We want lightweight, local signals that help decide when the bot should speak without changing core behavior yet.

## Goal
Provide a small "conversation poll" snapshot that can be used to decide whether the bot should respond, based on what happened since the bot last spoke.

## Non-Goals (for this phase)
- No new persistence layer.
- No deep semantic moderation or full conversation summarization.
- No changes to bot prompts or response text in this phase.

## Current Flow Notes (How Messages Move Today)
- `event_message` calls `_get_message_metadata`, then `add_to_appropriate_message_history` for every message.
- `message_history_raw` is cleared after BQ upload when it has 2+ messages, so it is not a stable window.
- `all_msg_history_gptdict` keeps GPT-ready strings, but does not preserve metadata fields.
- `add_to_thread_history` only queues non-bot authors; bot output is not added to the thread here.
- Bot output is sent through `_send_channel_message_wrapper`; it only re-enters `event_message` if Twitch IRC echoes bot messages and TwitchIO dispatches them (no explicit in-app reinsert, `message.echo` is not checked).
- `users_in_messages_list_text` is cumulative for the session and not pruned to a recent window.

## GPT Context Notes (Documentation Only)
- The OpenAI thread stores assistant messages generated by runs, so conversationdirector can already see prior assistant responses in the thread history.
- We do not currently inject bot messages from `event_message` into the thread (only user messages are queued); adding bot messages manually risks duplication.
- The rolling buffer is used for local gating/poll logic, not for GPT input; if we later feed it to GPT, include bot messages carefully to avoid repeats.
- Avoid prompt-specific story context injections; any cross-assistant context should come from shared history or thread sync, not one-off prompt hacks.

## Cross-Assistant Context (Next Steps)
- Problem: assistants on different threads (story/explain/vibecheck) do not share their outputs with `chatformemsgs`, so conversationdirector/randomfact may miss recent bot context.
- Option A: mirror bot outputs from non-`chatformemsgs` threads into `chatformemsgs` as assistant messages (skip if origin thread is already `chatformemsgs` to avoid duplicates).
   - I think this is the best way forward because then chatformemsgs ends up being our "MC" master of ceremonies for all bot outputs 
- Decision needed: which assistants should receive shared context, how to dedupe, and max context window size.
  - We should probably have a way where by any non-chatformemsgs thread that generates bot output should be mirrored into chatformemsgs thread as an assistant message.  This way chatformemsgs is always aware of what the bot has said most recently across all threads.  We can avoid duplication by checking the origin thread ID before adding the mirrored message.

## Rolling Buffer (Required)
- Add a `recent_message_metadata` list (or similar) that stores raw metadata for the last N messages.
- Append every inbound message after `_get_message_metadata`.
- Bot outputs are captured via `event_message` echo; only add send-time records if echo is disabled.
- Keep size limited by a new `msg_history_limit`
- Use this buffer to compute "since last bot message" slices and timestamps.
Config keys (proposed):
- `conversation_poll.window_size`
- `conversation_poll.message_count_threshold`
- `chatforme_randomfacts.randomfact_sleeptime`

## Proposed Snapshot (Since Last Bot Message)
- last_bot_message_id
- last_bot_message_timestamp
- last_bot_message_source (twitch_event, local_send, thread_only)
- last_bot_message_origin (randomfact, chatforme, command, system)
- messages_since_last_bot_count
- unique_users_since_last_bot_count
- per_user_message_counts (since last bot message)
- messages_with_bot_mention_count
- command_message_count
- last_command_timestamp (optional)
- last_command_name (optional, parsed from leading token)
- time_since_last_bot_message_seconds
- recent_messages_sample (last N user messages, optional)

## Data Inputs (From Existing Metadata)
Use fields already present in message metadata:
- name, user_id, display_name
- channel, timestamp
- content (already cleaned by command spellcheck)
- role, interaction_type
- message_id
Notes:
- Bot messages will show up as `role='user'` if `event_message` receives them, so role alone is not enough.
- `interaction_type` marks bot mentions as `command`, so bot mention counts should not rely on command filtering alone.

## Decisions (Current)
- Use a rolling buffer of raw message metadata for poll computation.
- Commands do not count toward general activity, but bot mentions inside commands do count because the bot will likely already respond to the command and we have a command specifically if the user @/tags the bot.
- Poll gating applies to chatforme/randomfact only; long-form sessions (story/explain/factcheck) continue unless explicitly coordinated.
- No multi-channel behavior is required.
- A configurable message-count threshold triggers an "immediate" next scheduled chatforme/randomfact run (single-shot flag, still subject to gate checks).
- After an immediate run, reset any temporarily shortened sleep time back to the configured `randomfact_sleeptime`.

## Decision Examples (Downstream Usage + Alternatives)
- If unique_users_since_last_bot_count >= 2, do not interject.
- If one user has >= 2 messages since last bot message.  We could add functionality to "consider replying only if asked or implicitly addressed" but only do this if we can make use of existing functionality, maybe our existing Open AI tool for "response_type" can be reused here.
- If messages_with_bot_mention_count >= 1, prioritize a reply. (Let's seriously review this because it may conflict with other rules, e.g. right now i thinkt here is already a command that checks for the bot mention and especially if it's tagged/@ so let's not duplicate that logic here which could deterioate user experience)
- If time_since_last_bot_message_seconds > randomfact_sleeptime, allow a reply unless chat is active. (this one sounds like a heavy logic change /refactor, so  let's review carefully and decide whether this is maybe overkill.  If some of our other polling and stuff already presents an interface for this, we can reuse that instead of adding more complexity)
- Conversationdirector may return `respond`, `fact`, or `anybody_there` based on thread context and recency.
- We do not need to check for qualifying commands here, they are handling themselves.  The things we're checking for are messages, not commands.  Commands have specific functions assocated with them already and will trigger accordingly.  Our focus here is trying to get better at dealing with a flow of messages which need interpretation which we'll mimic by some simple logic to gate/allow the bot to respond.
 - If the immediate-next-run path shortens `randomfact_sleeptime`, restore it to the configured value after the run.
Operational detail:
- Commands (messages starting with "!") should not increase general activity counts, but bot mentions within those commands should still increment `messages_with_bot_mention_count`.
Alternatives / tradeoffs:
    - Use a simple activity score (unique_users * message_count) instead of hard gates.
    - Permit a response when chat is active but bot was directly mentioned or asked a question ( a lot of our control flows already handle this, so let's not duplicate logic here, take a look before you add anything new here)
    - Use a time-based cool-down (which is already set with the randomfact_sleeptime I think) plus a short recent-message window rather than a hard count.

## Open Questions
- What counts as a "bot message"? (assistant role only, bot username only, or any message sent by the bot process)
  - This needs a full evaluation of pros/cons. Assistant role is tricky because threads can be long-lived. Bot-username-only is simpler but can miss edge cases. Any message sent by the bot process is most robust but may be overkill for now.
- Should messages from the streamer/mods/bots be excluded from unique user counts?
  - a toggle for mod exclusion could be useful.
- What happens if the last bot message is not in the in-memory window (history limit)?
  - keep a dedicated rolling buffer, but also accept "unknown" and default to safe behavior.
- Should the snapshot reset on any bot output, or only on certain message types
    - I think here we should be limiting the reset to only certain message types. startstory and fact check are our only long runnning threads really, so i think that those shouldn't reset our counters and things here.  For example if someones used !startstory and it's on message 6 but meanwhile two users have had conversations and the bot decides it's a good time to respond/add value, it shouldn't be blocked because of the long running thread.  This note has implications elsewhere in this doc so cirlce back to it if necessary
- Do we want a simple dedupe check on recent bot outputs to reduce near-repeats?
  - Leaning no: GPT outputs vary slightly and we do not want FAISS-based dedupe here.  We want to identify places where this coudl be happnening naturally and try to correct the upstream cause
- Should we treat commands containing bot mentions as a separate signal (mention + command) for priority replies?
    - Again, I think we should avoid duplicating logic here.  If a command contains a bot mention, our existing command handling logic should already be taking care of prioritizing that response.  IF you see gaps you can call them out but probably bes to leave it for now.
- Which command types should reduce scheduled chat delay (all commands, only content-creation commands, or only direct mentions)?
    - To be honest the only thing that should be reducing dealy is messages.  Commands have their own flow and should not be mixed up here.  So I think we should avoid adding any command-related logic to this section.  The only exception is if a command contains a bot mention, in which case our existing command handling logic should already be prioritizing that 
- What is the intended "threshold rule" before the immediate-next-run flag is allowed (count threshold, cool-down, or per-command allowlist)?

## Assistant Coordination Options (Non-Gating)
- Priority bands: allow randomfact/chatforme to coexist, but de-prioritize bot responses when a long-form assistant (story/explain) is active.
- Cooldowns by assistant type: short cooldowns for chatforme, longer for randomfact, none for story/explain unless explicitly stopped.
- Topic ownership: when a long-form session starts, annotate a "current topic" and let chatforme only answer direct mentions or questions.
- Soft arbitration: if two assistants are scheduled within a short window, prefer the one that is user-triggered (command/mention) over scheduled.

## Future Options (Post-MVP)
- Light semantic summarization or topic drift detection to reduce "repeat-ish" replies.
- Optional per-user thread summaries (low-cost) to avoid repeating advice to the same chatter.
